# Research: Why typed (keystroke-injected) text loses fidelity in terminals, and a real paste does not

Why River's auto-inserted transcript sometimes loses text, or shows `[Pasted text #N ...]` placeholders, when the target is Claude Code's TUI inside VS Code's integrated terminal, while "Copy last transcription" + Cmd+V is lossless. Researched 2026-10-12 against `fix/paste-fidelity` (River inserts via `CGEvent` Unicode key events, 20 UTF-16 units per event, no delay between events). Sources are numbered in §8. Anything marked **(inferred)** or **(anecdotal)** has no primary-source confirmation. Claude Code is closed source, so its input heuristics are known only from its docs and issue reports.

## 1. Summary

- **Real paste is a different channel from typing.** xterm.js (VS Code's terminal) wraps clipboard paste in `ESC[200~ ... ESC[201~` when the app enabled mode 2004, and it writes the wrapped text as one `triggerDataEvent` [11][21][22]. Ink-based apps enable that mode and route the bracketed block to a separate `paste` event, never to the key handler [3]. Synthetic keystrokes never take that path, so a typed insertion looks to the app like very fast typing.
- **Claude Code does collapse pastes, and the documented trigger is size:** more than 800 characters or more than three lines becomes `[Pasted text #N +X lines]` [1]. The docs do not say whether unbracketed input can trigger it. Nothing in the primary sources confirms an unbracketed-burst heuristic **(inferred)**; the placeholder River's user sees is the strongest evidence that one exists.
- **Claude Code's docs admit lossy delivery in VS Code:** "The VS Code integrated terminal can also drop characters from very large pastes before they reach Claude Code" [1]. Open issues show silent truncation and dropped text in several input paths [4][5][6][8].
- **Multi-unit synthetic events are translated lossily by Chromium and xterm.js (the leading structural suspect).** Chromium derives the DOM `key` for a macOS key event from the *last* Unicode character of `NSEvent.characters` [16]. xterm.js sends `ev.key` when it is one character and then cancels the event, so the browser's text-input path never delivers the rest of the chunk [12][14]. This is **(inferred)** from two source reads, not observed. If true, it predicts loss on nearly every chunk, which is more than "sometimes" (§5, H2).
- **Apple warns that frameworks may ignore the Unicode string** and translate from the virtual key code instead [17]. The ~20-unit limit is **(anecdotal)** [18]; Apple documents no limit [17].
- **Recommended first step is measurement, not mitigation:** record the raw bytes the terminal writes to the pty for one 20-unit chunk, with and without kitty keyboard protocol (§5). That single experiment separates H1 and H2 and costs nothing.

## 2. How Claude Code and Ink detect pastes

- **Ink (documented behaviour).** Ink's `useInput` is "called for each character"; if the user pastes more than one character "the callback will be called only once, and the whole string will be passed as `input`" [3a]. So even unbracketed multi-character stdin arrives as one string.
- **Ink bracketed paste.** `usePaste` calls `setBracketedPasteMode(true)` (`ESC[?2004h`) and the stdin parser emits bracketed blocks on a separate `'paste'` channel, "never forwarded to `useInput` handlers" [3b][3c]. Ink buffers an incomplete escape sequence for 20 ms (`pendingInputFlushDelayMilliseconds = 20`) before treating it as literal input [3c].
- **No heuristic in Ink itself.** The surveyed Ink sources contain no "fast input is a paste" timer. Claude Code ships its own Ink-derived TUI, so any such heuristic would live there and is not publicly readable **(inferred)**. *Confirmed 2026-10-12:* the source bundled in Claude Code 2.1.296 treats any key input longer than 800 characters without bracketed-paste markers as a paste, and a pty loop against the real binary reproduced H1 ([../planning/0031_terminal-insert-fidelity.md](../planning/0031_terminal-insert-fidelity.md)).
- **Claude Code enables bracketed paste.** Issue #91205 shows `ESC[?2004h` among the modes it sets, alongside kitty/mouse/focus modes [4].
- **Collapse rule.** More than 800 characters or three lines becomes a placeholder; the full content is still sent on submit; large pastes are better written to a file [1]. Users ask for a threshold setting or a disable switch (#23134, #85453), so the 800/3 values are fixed today [1][8a].
- **Pasted content is tagged.** On submit Claude sees each placeholder's content marked as pasted-from-elsewhere, and is told to follow instructions inside it only if the typed message asks [1]. A transcript that arrives as a placeholder therefore changes how the model treats it.
- **Known loss and reordering reports (all open unless noted):**
  - #91205: a bracketed block followed by a key *in the same stdin chunk* drops the pasted text, reproduced against real `claude` in a pty. Fast links work, slow links that coalesce the following key into the same read fail [4].
  - #86954: a bracketed paste delivered about 0.7 s after launch is truncated to a prefix (1011 of 3722 characters), 100% reproducible. The same report shows idle-prompt Cmd+V and mid-stream API paste are lossless (3722/3722) [5].
  - #90910: on macOS in Warp, the first two thirds of a long prompt (typed, not pasted) were silently dropped, intermittently (5 of 14 prompts in one day). The reporter concludes the fault is "how Claude Code consumes a large input burst" [6].
  - #98959: the prompt sticks on "Pasting..." until another key arrives, which implies a paste state machine that waits for the end marker [7].
  - #49337 and #49673 (closed): large pastes trimmed from the start or the end on Windows [8b].

## 3. How synthetic Unicode key events reach a terminal

- **What the API promises.** `keyboardSetUnicodeString` lets you "manually override" the string; "application frameworks may ignore the Unicode string in a keyboard event and do their own translation based on the virtual keycode and perceived event state." Apple documents no length limit [17].
- **The 20-unit limit is folklore.** A Qt forum post reports "ONLY 20 characters are always sent" **(anecdotal)** [18]. River's `keystrokeChunkUnits = 20` follows it [25].
- **Prior art posts tiny events.** Hammerspoon's `keyStrokes` posts one UTF-16 unit per key-down/up pair to the HID tap with no `usleep`, copied from an Apple mailing-list snippet [19]. No surveyed source shows 20-unit events being safer than 1-unit events.
- **Chromium (VS Code is Electron).** `DomKeyFromNSEvent` reads the last Unicode character of `characters` to build the DOM `key`, because a dead-key sequence can prepend earlier characters. `KeyboardCodeFromKeyCode` maps the physical key, so virtual key 0 is the `A` key (`KeyA`, keyCode 65) [16]. So a 20-unit chunk arrives as a `keydown` with `key` = its last character and `code` = `KeyA` **(inferred from a WebFetch summary of [16]; confirm in source)**.
- **xterm.js key path.** `_keyDown` calls `evaluateKeyDown`; legacy mode sets `result.key = ev.key` only when `ev.key.length === 1` and no ctrl/alt/meta; then `triggerDataEvent(result.key)` and `preventDefault()` [12][14]. The `input` event handler (`insertText` -> `triggerDataEvent(ev.data)`) is the path that would carry a whole multi-character string as one write, but it only fires if `keydown` was not cancelled [12].
- **Kitty keyboard protocol changes the path.** xterm.js now implements it [13]. With flags set, the encoder derives the key code from `ev.key.codePointAt(0)` only when `ev.key.length === 1`, and reports associated text only for a one-character key [13]. Whether Claude Code pushes flags in VS Code is unconfirmed; its 2.1.269 changelog touched kitty input parsing, and dictation tools broke in VS Code until users set `terminal.integrated.enableKittyKeyboardProtocol: false` [9]. xterm.js #6112 shows the protocol alone changes how IME commits are delivered (a single-character commit became a space byte) [15].
- **No bracketed-paste wrapping for typed input.** `bracketTextForPaste` runs only from the paste handlers [11]; `_keyDown`/`_inputEvent` call `triggerDataEvent` directly [12]. So the answer to "does xterm.js wrap synthetic key events in `ESC[200~`?" is no, from source. Mode 2004 is defined by xterm's control-sequence spec [22].
- **Ordering and coalescing.** Nothing in the primary sources says the HID tap reorders events. The pty is a byte stream, so xterm.js writes reach Claude Code in order but may be coalesced into one `read` (#91205 shows coalescing matters) [4]. VS Code's `sendText`/paste goes through one `processManager.write` with no chunking in the visible code [21]. A tty input queue is capped at `MAX_INPUT` and the kernel discards characters beyond it when it cannot accept them [24]; whether the pty master write path blocks instead of dropping was not verified **(inferred; low likelihood, #86954 ruled out the kernel pty for Cmd+V)** [5].
- **Terminal.app and iTerm2.** No primary source found on multi-unit synthetic events. A Keyboard Maestro thread shows iTerm2 mishandling synthesized option-key combinations and offers a hidden `ForceInsertTextByUnicode` preference **(anecdotal)** [20]. River's 0011 note records that terminal insertion passed on-device [25], so the failures here are probably specific to xterm.js plus Claude Code.

## 4. Why real Cmd+V is lossless

- **Wrapped and atomic.** VS Code's paste action calls xterm's `paste()`: `prepareTextForTerminal` (newlines to `\r`), `bracketTextForPaste` (`ESC[200~ ... ESC[201~`, ESC in the text replaced by U+241B) when `decPrivateModes.bracketedPasteMode` is on, then one `triggerDataEvent` [11][21].
- **The app has a dedicated path.** Ink delivers the block as one `paste` event [3b][3c]. Claude Code owns the placeholder logic for exactly this input [1], and the user's observation (lossless) matches #86954's idle-prompt Cmd+V result [5].
- **Residual risks even for real paste:** a key coalesced after the end marker (#91205 [4]), a stuck end marker (#98959 [7]), startup timing (#86954 [5]), and very large pastes in VS Code [1]. A dictated transcript is small and arrives with no following key, so none of these should apply.

## 5. Ranked mechanisms and falsifiable predictions

Run the experiment in §5a first; it decides H1 versus H2.

**5a. Cheap discriminator (no River change).** In the VS Code terminal run `stty raw -echo; cat -v` (the recorder used in [9]), insert one 20-character chunk with River, and read the bytes. Repeat after pushing kitty flags (`printf '\e[>1u'`) and with `terminal.integrated.enableKittyKeyboardProtocol: false`. Then repeat inside Claude Code with a ~100-character transcript.

- **H1. Claude Code treats a burst of unbracketed input as a paste (explains placeholders and intermittency).** Rationale: placeholders appear in typed text; a paste state machine exists ("Pasting..." [7]); burst-consumption loss is reported [6]; coalesced reads break bracketed handling [4]. *Prediction:* the 5a recorder shows all characters arriving, but Claude Code loses or collapses them. Adding a 50-150 ms delay between chunks, or sending one chunk, makes the placeholder and the loss disappear. Text under ~20 units never fails. Failure rate rises with transcript length and with machine load.
- **H2. xterm.js/Chromium keep only the last character of each multi-unit event.** Rationale: §3 (Chromium last-character `key`, xterm.js cancel after sending `ev.key`) **(inferred)**. *Prediction:* the 5a recorder shows one byte per chunk, or a CSI-u sequence for the last character, when the chunk ends in a lowercase letter or punctuation; whole chunks arrive when it ends in A-Z (the xterm.js A-Z keypress workaround, `_keyDown` skips A-Z so the `input` path delivers the text [12]). Sending one UTF-16 unit per event (Hammerspoon style [19]) makes the loss vanish. Turning kitty protocol off changes the pattern. Caveat: if H2 were fully true, loss would be near-constant, so only a partial form of it fits "sometimes".
- **H3. Kitty-protocol interaction in VS Code (variant of H2).** *Prediction:* the loss appears only when Claude Code has pushed kitty flags, and `terminal.integrated.enableKittyKeyboardProtocol: false` removes it; Terminal.app and iTerm2 are unaffected [9][15].
- **H4. Rapid posting outpaces delivery or coalesces reads.** *Prediction:* the 5a recorder is clean; loss correlates with Claude Code being busy (streaming, rendering) and vanishes when the target is idle; an inter-chunk delay of tens of ms fixes it [4][6]. No primary source shows a macOS event-queue drop **(inferred)**.
- **H5. Large-input drop in VS Code.** *Prediction:* loss only on transcripts over a few hundred characters; the docs acknowledge it for large pastes [1]. Weaker, because the River transcripts are typed, not pasted.

## 6. Mitigation options and tradeoffs

- **Pasteboard + synthetic Cmd+V, then restore the clipboard.** Reuses the lossless real-paste path in every app, including bracketed paste in xterm.js [11][21]. Costs: the clipboard-restore race that planning 0011 removed (restore timing against a paste River cannot observe) [25]; clipboard-manager capture, mitigated by marking the item with `org.nspasteboard.TransientType`/`ConcealedType`/`AutoGeneratedType` [23]; a user-visible clipboard change if restore fails; Claude Code treats Cmd+V specially in some terminals (image-paste fallback, double-paste in Ghostty #96387; literal `v` in VS Code #44044 was closed) [2][8c][10]. A transcript over 800 characters or three lines will be collapsed to a placeholder, with the content still sent [1].
- **Emit bracketed-paste markers via keystrokes.** Not viable as a plain fix: an `ESC` typed as a Unicode string is not a pty-level escape, and xterm.js only wraps real pastes [11][12] **(inferred)**. River has no pty access, and sending `ESC[200~` to an app that did not enable 2004 would insert garbage [22].
- **Pace chunks (delay 20-100 ms) or shrink to 1 unit.** Cheap and keeps the no-clipboard design. Tests H1/H2/H4; Hammerspoon shows 1-unit events are an accepted pattern [19]. Costs: dictation of ~1000 characters takes seconds at 1-unit-per-event with delays, and pacing leaves the placeholder risk if H1 is time-based on total length.
- **Per-target strategy.** Detect a terminal as the frontmost app by bundle ID (River cannot see `TERM_PROGRAM`) and use paste there, keystrokes elsewhere. VS Code's bundle ID cannot tell a terminal pane from an editor pane, so the table would be coarse. Adds a target table to maintain.
- **Mixed approach (inferred).** Use the pasteboard path only when the transcript exceeds a threshold or the target is a known terminal, keeping the no-clipboard guarantee for ordinary text fields. Not evidenced by any source; it is a design idea.

## 7. Open questions

- Which flags does Claude Code push in VS Code, and does it treat a multi-character unbracketed read as a paste? Not answerable from public sources; testable with §5a and by inspecting the bytes Claude Code receives.
- Does Chromium suppress the text-input path after an xterm.js-cancelled `keydown` for a synthetic multi-unit event? Needs a one-off run in Electron.
- What was the exact failing transcript (length, newlines, trailing key)? Placeholder appearance needs the 800/3-line rule [1] checked against it.
